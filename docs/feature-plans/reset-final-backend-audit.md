## Resolved findings

- **Stale external storage deletion:** the database reset atomically advances an immutable storage generation and asserts exact state ownership before commit (`backend/src/modules/system-reset/system-reset.database.ts:380-401`). All central and direct upload writers use that generation, including module covers (`backend/src/modules/system-reset/system-reset.context.ts:18-45`; `backend/src/modules/file-upload/storage/storage.service.ts:43-79`; `backend/src/modules/content-modules/module-cover-upload.util.ts:103-110`). Local/S3 cleanup preserves the current generation and deletes only retired keys (`backend/src/modules/file-upload/storage/reset-local-storage.ts:90-96`, `163-201`; `backend/src/modules/file-upload/storage/reset-s3-storage.ts:59-64`, `244-298`). The coordinator joins an active cleanup tick during graceful shutdown (`backend/src/modules/system-reset/system-reset.service.ts:125-136`, `653-661`), and the lease-loss regression proves a delayed retired-generation delete cannot remove a same-name fresh object (`backend/test/system-reset-coordinator.integration-spec.ts:616-674`).
- **Stable storage ownership:** local storage requires a protected UUID sentinel, and S3 requires the matching protected control object. Both are included in `ownershipHash` and rechecked throughout cleanup (`backend/src/modules/file-upload/storage/reset-local-storage.ts:16-87`, `139-175`; `backend/src/modules/file-upload/storage/reset-s3-storage.ts:25-57`, `215-262`). Recovery compares locator and ownership identity (`backend/src/modules/system-reset/system-reset.service.ts:597-621`). Same-locator/different-identity tests fail before deletion (`backend/src/modules/file-upload/storage/reset-local-storage.spec.ts:97-108`; `backend/src/modules/file-upload/storage/reset-s3-storage.spec.ts:220-230`).
- **Materialized-view scope:** public materialized views are discovered and fail closed before inventory/reset (`backend/src/modules/system-reset/system-reset.database.ts:133-150`). Disposable-PostgreSQL coverage proves a view cannot silently retain a row (`backend/test/system-reset.integration-spec.ts:107-129`).
- **Graceful participant retirement:** migration `0026` adds durable retirement. New operations exclude retired rows while already-required IDs remain visible to recovery (`backend/drizzle/0026_system_reset_participant_retirement.sql:1`; `backend/src/modules/system-reset/system-reset.service.ts:204-212`). Backend and AI shutdown serialize their final current-epoch acknowledgement/retirement with reset claim on `RESET_WRITE_LOCK`; AI clears its cache before committing retirement (`backend/src/modules/system-reset/system-reset.participant.ts:236-280`; `ai-service/app/system_reset.py:107-124`, `259-279`). Real-PostgreSQL tests cover retirement before claim and claim before retirement (`backend/test/system-reset-coordinator.integration-spec.ts:249-320`; `ai-service/tests/test_system_reset_postgres.py:150-196`).
- **Hard-loss safety boundary:** before participant acknowledgement or cleanup, the coordinator must own `RESET_IO_LOCK` exclusively. It considers only captured rows with an expired heartbeat and durable `in_flight=0`; it never clears a busy marker (`backend/src/modules/system-reset/system-reset.service.ts:557-596`, `735-811`). Participant retirement and the operation's `hardRetiredParticipants` receipt are committed by one data-modifying CTE statement, so PostgreSQL cannot persist one without the other (`backend/src/modules/system-reset/system-reset.service.ts:565-595`). Coordination accepts retired required evidence but still rejects any current non-retired stale epoch (`backend/src/modules/system-reset/system-reset.coordination.ts:4-23`). Real-PostgreSQL coverage proves a shared I/O lease prevents idle retirement, an expired idle row becomes eligible only after exclusive acquisition, an expired `in_flight=1` row remains in draining without storage purge, and an injected receipt-update failure rolls both logical changes back before a successful retry persists both (`backend/test/system-reset-coordinator.integration-spec.ts:407-544`).

## Confirmed safeguards

- The active, verified acting administrator is locked and retained; all other users and role links are deleted, exactly one admin role is recreated, the password is unchanged, and `session_version` advances atomically. Verification requires one user, one role link, one academic state, and the designated year/period (`backend/src/modules/system-reset/system-reset.database.ts:291-405`, `408-447`).
- Database deletion is transactional, child-before-parent, runtime-catalog checked, and protected by statement barriers. Retained nullable references are snapshotted before detachment and restrictive legacy evidence is archived (`backend/src/modules/system-reset/system-reset.database.ts:133-245`, `248-405`).
- Access JWT validation checks `session_version`; refresh grace hits require a live database successor; Redis grace keys are removed; notification sockets disconnect on maintenance/epoch change (`backend/src/modules/auth/strategies/jwt.strategy.ts:35-61`; `backend/src/modules/auth/token.service.ts:63-80`; `backend/src/modules/system-reset/system-reset.queues.ts:185-227`; `backend/src/modules/notifications/notifications.gateway.ts:78-137`).
- Redis cleanup is atomically fenced by epoch/generation and retains pause metadata until restoration (`backend/src/modules/system-reset/system-reset.queues.ts:11-51`, `105-141`, `185-242`). AI admission records durable busy state, holds the shared I/O lease, reapplies the request epoch to each database transaction, drains before cache acknowledgement, and clears materialized backend-upload cache (`ai-service/app/system_reset.py:68-152`, `207-279`; `ai-service/app/database.py:9-33`; `ai-service/app/backend_uploads.py:19-34`).
- Migrations `0022` through `0026` are journaled in order, preserve the migration ledger, install statement barriers, add participant in-flight/retirement state, and introduce storage generation with a legacy default (`backend/drizzle/meta/_journal.json:159-193`). CI rehearses reset on PostgreSQL 16/18 with disposable Redis and exercises AI PostgreSQL reset behavior; the AI deployment follows the tested backend deployment (`.github/workflows/ci.yml:81-154`, `215-253`; `.github/workflows/railway-deploy.yml:104-134`). Reset and destructive ownership flags default off.

## Verification boundary

No live S3/R2/Railway bucket acceptance was run. An expired participant that still has durable `in_flight>0` intentionally leaves reset in draining; automatic retirement would be unsafe without authoritative process-death fencing. This is the correct fail-closed boundary, not proof of automatic recovery from every host failure. Keep the destructive reset flags off until deployment-specific storage ownership and recovery checks are completed.
