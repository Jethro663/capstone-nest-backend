This diagram is grounded in the current repo flow across next-frontend, backend, and ai-service. It traces what happens from the user click, to the Nest controller and service path, to the exact places where Python actually runs, and back to the UI.

Core Truths LXP Path List LXP Detail + Progress LXP to JA Review Bridge Student Tutor Python Path PDF Extraction Pipeline Extraction Apply Improvement Hotspots

Three Core Truths Before You Read the Flow

  • Most of student LXP is not Python-driven. The path list, overview, playlist, checkpoint progress, and intervention-case closure are primarily Next.js -> NestJS -> PostgreSQL.
  • Python appears when the learner leaves plain LXP and enters an AI surface: student tutor, JA review generation, or PDF/module extraction.
  • Assessment retry checkpoints inside LXP are intentionally completed outside the plain LXP endpoint. The real completion bridge is LXP -> JA Review -> JA completeSession() -> LxpService.completeAssessmentRetryFromJaReview().

The user route, click, state transition, and rendered result in the dashboard.

Database

Drizzle or SQL-backed reads and writes across enrollments, intervention cases, LXP progress, extracted modules, and content tables.

FastAPI routes, tutoring logic, retrieval, extraction, graph assembly, rule fallback, and apply logic.

Model and Rules

Ollama generation, JSON-schema output, deterministic objective grading, and rule-based extraction fallback.

Flow A: Student Opens The LXP Path List

Route: /dashboard/student/lxp. This is the first important distinction: this page does not ask Python to "generate LXP". It asks backend LXP logic to compute which intervention paths already exist for the student.

Primary intent

Show active or completed Learners Path cases and counts per class.

Main endpoint

GET /api/lxp/me/eligibility

Python involved?

No. This is computed from enrollments, performance snapshots, intervention cases, and intervention assignments.

Browser

Student opens the LXP page

The App Router renders StudentLxpPage, which returns StudentLxpExperience.

Cards appear with path counts

The student sees per-class intervention state, score context, pending steps, completed checkpoints, and subject metadata.

Next Frontend

Component normalizes legacy route state

StudentLxpExperience checks query params in useEffect(). Old LXP-to-JA patterns are redirected into the newer routes when needed.

Path fetch starts

fetchPaths() calls lxpService.getEligibility(), then maps response.data.paths into rendered cards.

Nest Backend

LxpController delegates immediately

getEligibility() is a thin route wrapper on GET lxp/me/eligibility. It passes the authenticated student id to LxpService.getStudentEligibility().

Database

Service computes path inventory

  • Reads enrollments for classes where the student is currently enrolled.
  • Reads performanceSnapshots to know isAtRisk, blendedScore, and threshold.
  • Reads interventionCases with status active or completed.
  • Reads interventionAssignments to compute step counts, replay counts, total, pending, and completion percent.

Backend assembles return payload

The payload includes threshold, eligibleClasses, and paths. Each path already contains class identity, case id, status, score context, and progress math.

AI Service Python

Not used in this flow

This page is a read-only LXP inventory page. No request is sent to ai-service.

Model and Rules

No generation stage

There is no model call, no retrieval, no prompt, and no Python-generated response involved in the initial path list.

The "LXP page" is mostly a projection over already-existing academic recovery state. If the student asks "why do I have this path?", the answer originates in performanceSnapshots and interventionCases, not in a live Python generation.

Flow B: Student Opens One LXP Path And Works Through Steps

Route: /dashboard/student/lxp/[classId]. This page is where the student sees overview data, ordered checkpoints, lesson-review actions, and assessment-retry handoffs.

Primary endpoints

GET /api/lxp/me/overview/:classId and GET /api/lxp/me/playlist/:classId

Backend job

Validate enrollment, validate active case, ensure default assignments, compute progress, then shape the UI-friendly response.

Python involved?

Still no for plain detail loading and lesson-review completion. Python starts only when the student jumps into AI surfaces from here.

Browser

Student clicks a path card

The list page uses router.push('/dashboard/student/lxp/:classId').

UI renders tabs and checkpoints

The page separates steps, replays, case, and overview while keeping the path state in sync.

Student completes a lesson-review checkpoint

The "mark complete" action only applies to lesson_review checkpoints. Retry checkpoints are blocked here by design.

Next Frontend

Detail component starts two requests in parallel

StudentLxpDetailExperience calls Promise.all([lxpService.getOverview(), lxpService.getPlaylist()]) inside fetchDetail().

Checkpoint completion request

lxpService.completeCheckpoint(classId, checkpointId) is called only when the checkpoint is not read-only and not an assessment retry.

Frontend refreshes state after completion

After completion, the page stores the returned playlist, re-fetches overview, and re-renders the progress meter and next actions.

Nest Backend

Overview controller path

LxpController.getOverview() routes to LxpService.getStudentOverview(studentId, classId).

Playlist controller path

LxpController.getPlaylist() routes to LxpService.getStudentPlaylist(studentId, classId).

Completion controller path

LxpController.completeCheckpoint() routes to LxpService.completeCheckpoint().

Audit and notify on close-out

If all assignments become complete, the service writes audit events and sends a teacher notification that the intervention cycle is done.

Database

Shared guards before data shaping

  • assertStudentEnrollment() ensures the student belongs to the class.
  • getReadableStudentInterventionCase() looks for an active or completed path case.
  • If only a pending case exists, the backend throws "pending teacher approval".

Default assignments and progress are materialized

For active cases, ensureDefaultAssignments() runs before returning data, and the service loads or creates lxpProgress.

Overview payload is assembled

  • Reads current class snapshot and all enrolled-class snapshots.
  • Builds subjectMastery, recommendedAction, upcomingAssessments, recentActivity, and weakFocusItems.
  • Uses intervention status plus progress to derive the status summary.

Playlist payload is assembled

The ordered checkpoint list comes from interventionAssignments joined to lessons and assessments, plus a progress summary from lxpProgress.

Lesson-review checkpoint transaction

  • Validates the assignment belongs to the current student and class.
  • Rejects completion if the case is inactive.
  • Rejects completion if the assignment type is assessment_retry.
  • Marks the assignment complete, updates lxpProgress, and checks whether every assignment is now done.

Case may auto-close

If every assignment in the case is completed, the service updates interventionCases.status to completed, sets closedAt, and appends an auto-completion note.

AI Service Python

Not used for plain detail or lesson-review completion

The detail page itself stays in the Nest and database boundary until the student chooses a JA or tutor action.

Model and Rules

No live model call here

Progress calculation, next-step selection, and checkpoint closure are deterministic service logic.

Overview response contains

  • selectedClass
  • interventionStatus
  • progress
  • subjectMastery
  • recommendedAction
  • upcomingAssessments
  • recentActivity
  • weakFocusItems

Playlist response contains

  • interventionCase
  • progress
  • checkpoints[] with lesson_review or assessment_retry
  • Linked lesson metadata or linked assessment metadata per checkpoint

Flow C: LXP Assessment Retry Does Not Finish Inside LXP

This is the most important hidden bridge in the module. When the student clicks a replay checkpoint, the detail page routes them into JA review. The checkpoint is only completed after JA session completion, not when the student clicks inside LXP.

Why this matters

If you want to improve LXP retry behavior, the real closing logic lives in backend/src/modules/ja/ja.service.ts and then bounces back into LxpService.completeAssessmentRetryFromJaReview(). If you change only the LXP page, you will miss the actual completion seam.

Browser

Student clicks a replay checkpoint

The LXP detail page builds a JA review link using mode=review, classId, entry=lxp, and a returnTo route back to the replay tab.

Student answers the JA review session

The review UI runs its own cycle until the student completes all required items.

Next Frontend

Frontend leaves LXP and enters JA

The replay card uses /dashboard/student/ja?...mode=review.... From there, jaService handles review bootstrap, session generation, responses, events, and completion.

Nest Backend

Backend JA routes proxy into ai-service

ja.service.ts forwards review-session generation to /student/ja/review/sessions/generate through AiProxyService.

JA completion becomes the LXP bridge point

In completeSession(), if the session mode is review, the service looks for a linked assessment id in the JA source snapshot.

JA calls back into LXP service

completeSession() calls lxpService.completeAssessmentRetryFromJaReview(studentId, session.classId, linkedAssessmentId, sessionId).

Database

JA completion writes its own progress first

jaSessions, jaSessionResponses, jaXpLedger, jaProgress, and jaSessionEvents are updated before the LXP checkpoint bridge runs.

LXP retry checkpoint is marked complete

  • Finds the retry assignment by assessmentId.
  • Validates student, class, and active case.
  • Marks that intervention assignment complete.
  • Updates lxpProgress.
  • Optionally closes the intervention case if all assignments are done.

Audit trail keeps the source

The LXP audit metadata records source: 'ja_review' and the originating jaSessionId.

AI Service Python

JA review packet is generated in ai-service

ai-service/app/main.py exposes /student/ja/review/bootstrap and /student/ja/review/sessions/generate. This is where the AI-side review packet is built.

Model and Rules

Review content is AI-generated before the student answers

The review packet is created on the Python side. The exact challenge content lives in the JA AI path, then the Nest JA service owns the completion ledger and bridge back to LXP.

Hidden dependency to remember: if JA review breaks, LXP replay completion also breaks, because LXP retry checkpoints depend on JA session completion to close them.

Flow D: The Python Generation Path Closest To LXP Student Support

If your goal is "show me the Python generation path", the clearest student-facing example is the tutor flow. This is where Nest forwards to Python, Python retrieves class evidence, calls the model, stores session state, and sends generated tutoring output back.

Main frontend service

next-frontend/src/services/ai-service.ts

Main backend route group

/api/ai/student/tutor/*

Main Python owner

ai-service/app/student_tutor_service.py

Browser

Student opens tutor support

The browser asks for bootstrap data first: classes, recent lessons, recent attempts, recommendations, and history.

Student chooses one recommendation

The chosen focus item becomes the seed for the generated tutoring packet.

Student receives generated lesson and questions

The UI gets a session id, lesson plan, lesson body, practice questions, tutor plan, citations, and grounding status.

Next Frontend

Service wrapper calls backend AI routes

  • getStudentTutorBootstrap()
  • startStudentTutorSession()
  • sendStudentTutorMessage()
  • submitStudentTutorAnswers()
Nest Backend

Backend checks policy and source visibility

ai-mentor.controller.ts filters lesson ids and assessment ids the student is still allowed to see, then forwards the call with X-User-* headers.

Backend sanitizes citations on the way back

Returned citations are filtered again so the student only receives evidence linked to allowed lessons or assessments.

Database

Bootstrap gathers recent context

Python-side bootstrap reads the student's classes, recent lessons, recent attempts, and prior tutor history.

Retrieval pulls class-grounded evidence

_build_context_bundle() runs similarity_search() scoped by class, grade, subject key, and optionally lesson or assessment source ids.

Session state is persisted

_log_tutor_turn() stores tutor state and messages so the session can be reloaded and continued later.

AI Service Python

Python builds recommendations

bootstrap_student_tutor() and _build_recommendations() decide what the student most likely needs to review.

Python plans before writing

_plan_tutor_packet() asks the model for a JSON plan: teaching goal, misconceptions, required evidence, intended difficulty, and answer guardrail.

Python generates the lesson packet

_generate_lesson_and_questions() asks for lessonPlan, lessonBody, analogy, misconceptionCorrection, citationGrounding, and exactly 3 questions.

Follow-up messages and answer evaluation stay in Python

Later turns go through continue_student_tutor_session() and submit_student_tutor_answers().

Model and Rules

Model call 1: plan generation

ollama_client.generate(... task='chat', response_format=TUTOR_PLAN_FORMAT)

Model call 2: tutoring packet generation

ollama_client.generate(... response_format=TUTOR_PACKET_FORMAT). If anything fails, Python falls back to a conservative packet builder.

Answer checking is hybrid, not fully free-form

_evaluate_answers() can use the model, but _apply_deterministic_override() and evaluate_objective_answer() force objective corrections when the question type allows it.

This tutor path is a good example of "Python generation to output": request enters Nest, Nest proxies to FastAPI, FastAPI retrieves evidence, calls Ollama for JSON, stores state, and returns structured output to the browser.

Flow E: PDF or Module Extraction Pipeline

This is the most Python-heavy path in the repo. It starts from a teacher upload, creates an extraction record, runs in the background, then produces editable structured content plus audit metadata before anything is applied to live LMS content tables.

User click origin

next-frontend/app/(dashboard)/dashboard/teacher/classes/[id]/page.tsx

Main Python entry

POST /extract in ai-service/app/main.py

Core worker

run_extraction(db, extraction_id, file_id, user_id)

Browser

Teacher chooses a file for extraction

The teacher class page calls handleExtractionSelect() and then handleExtractionFile().

Teacher sees status change over time

The review route later polls every 3 seconds while extraction status is pending or processing.

Next Frontend

Frontend uploads the file first

fileService.upload() sends the PDF with classId, scope=private, subjectKey, gradeLevel, and aiEnabled=true.

Frontend queues extraction

After upload succeeds, extractionService.extractModule({ fileId }) hits the backend AI route.

Review page hydrates editable state

Once status becomes completed, the review page fetches full extraction content and clones sections into local edit state.

Nest Backend

Backend enforces access

POST /api/ai/extract-module runs assertTeacherFileAccess(), then forwards POST /extract through AiProxyService.forward().

Proxy adds identity headers

The backend forwards X-User-Id, X-User-Email, X-User-Roles, and optional X-Internal-Service-Token.

Backend later proxies status and detail routes too

/api/ai/extractions/:id/status, /api/ai/extractions/:id, and related review routes are all backend-proxied. Some have degraded cached fallback behavior if ai-service is unavailable.

Database

Python validates upload ownership and existence

  • Reads uploaded_files by id.
  • Checks teacher ownership unless the caller is admin.
  • Materializes the backend upload path.

Extraction row is created immediately

extracted_modules gets a new row with status pending and progress_percent = 0, then the API returns 202 with the new extractionId.

Structured output is persisted before the teacher edits it

When finished, the worker writes structured_content, model_used, chunk counts, progress, and final extraction status back into extracted_modules.

AI Service Python

Extraction is scheduled as a background task

/extract does not wait for the heavy work. It creates an async task that calls run_extraction() on the live event loop.

PDF ingest stage

  • Updates progress to 5 and 10.
  • Opens the PDF with fitz.
  • Extracts page text via _extract_pdf_pages().
  • Extracts embedded images via _extract_pdf_embedded_images().
  • Builds one raw text string across pages.

Branch decision: text path or vision path

If the PDF has almost no extractable text, Python switches to uses_vision_extraction = true. Otherwise it stays on the text-first path.

Text extraction path

  • sanitize_extracted_text() cleans the raw text.
  • _classify_content() can reject unsafe content before structure detection.
  • chunk_text(... max_chunk_size=8000) segments the module.
  • Each chunk goes through AI structure detection or rule fallback.

Graph and coherence assembly

  • _build_document_graph() creates section, span, question, and figure nodes.
  • _assemble_sections_from_graph() reassigns spans for coherence and merges weak fragments.
  • _attach_images_to_sections() scores image-to-section matches and adds image blocks.
  • _derive_section_assessment_draft() prepares draft checkpoint questions per section.

Audit and quality stage

Python computes overallConfidence, coherenceScore, warnings, qualityGate, reviewRequired, confidenceBreakdown, and repairNotes.

Validation and logging stage

validate_extraction_output() sanitizes the result, then Python logs a module_extraction record to ai_interaction_logs.

Model and Rules

Vision path model call

If the PDF is mostly scanned, ollama_client.generate(... task='vision_extraction') receives rendered page images and must return JSON with title, description, sections, and audit.

Text structure detection call

For readable PDFs, each chunk can go through _detect_structure_with_ai() using task='text_extraction'.

Rule fallback exists

If the AI structure detector fails or Ollama is unavailable, Python falls back to _detect_structure_with_rules() so extraction can still continue.

Model output is never trusted raw

The JSON is normalized, validated, rescored, and post-processed before it becomes the stored extraction result.

Stored extraction structure

  • title
  • description
  • sections[]
  • sections[].lessonBlocks[]
  • sections[].assessmentDraft
  • audit

Important audit fields

  • qualityGate = pass | warn | fail
  • reviewRequired
  • overallConfidence
  • coherenceScore
  • imageAssignmentSummary
  • reviewFlags
  • repairNotes

Flow F: Teacher Review, Save, And Apply Extraction Into Real LMS Content

The extraction result is intentionally not live LMS content yet. It becomes live draft content only after the teacher reviews, optionally edits, and explicitly applies it.

Review page

next-frontend/app/(dashboard)/dashboard/teacher/extractions/[id]/page.tsx

Save endpoint

PATCH /api/ai/extractions/:id

Apply endpoint

POST /api/ai/extractions/:id/apply

Browser

Teacher opens extraction review page

The page loads the extraction, shows status, quality flags, block-level content, section navigation, and apply controls.

Teacher edits and removes blocks locally

The review UI tracks removed block keys, section edits, focused items, and dirty state before persisting.

Teacher clicks Apply

Selected sections are sent for conversion into class modules, lessons, and draft assessments.

Next Frontend

Review page polls while processing

extractionService.getStatus(extractionId) runs every 3 seconds until the status changes to completed or failed.

Save serializes edited sections

handleSave() sends title, description, and sanitized sections. It can retry with legacy lessons payload compatibility if needed.

Apply sends selected section indices

handleApply() calls extractionService.apply(extractionId, { sectionIndices }), then reloads the extraction state after success.

Nest Backend

Backend proxies save and apply, then audits

The Nest controller forwards PATCH /extractions/:id and POST /extractions/:id/apply, then records audit metadata such as requested section counts and created artifacts.

Database

Save stage mutates only the extraction record

update_extraction() rewrites extracted_modules.structured_content. No live lessons or modules are created yet.

Apply reads extraction and class context

  • Checks the extraction exists, is completed, and is not already applied.
  • Loads normalized structured content and chosen sections.
  • Confirms the class still exists.
  • Finds next module order and next lesson order.

Apply creates the real LMS module shell

class_modules gets a new hidden and locked module with teacher notes showing it came from the extraction.

Each chosen section becomes concrete LMS rows

  • module_sections
  • lessons with source_extraction_id
  • lesson_content_blocks
  • module_items for the lesson

Assessment drafts are optionally created too

  • assessments with ai_origin = 'ai_extraction_draft'
  • assessment_questions
  • assessment_question_options
  • module_items for the assessment

Extraction is marked applied and class content is reindexed

After inserts, extracted_modules is updated to is_applied = true, status applied, then reindex_class_content() runs so retrieval can use the new content later.

AI Service Python

Python stays the owner through apply

Unlike many systems that only generate JSON, this Python service also owns the apply stage that writes module, lesson, block, and assessment rows.

Model and Rules

No fresh model call during apply

Apply uses the already-reviewed extraction result. The heavy generation happened earlier during run_extraction().

Conceptually, extraction has two completely separate phases: generate structured draft and apply reviewed draft into LMS tables. The second phase is a content-import operation, not an AI-generation operation.

Improvement Hotspots You Can Attack Next

These are grounded from the current implementation shape, not generic advice. They are useful if your goal is to make LXP or extraction more robust, faster, or easier to maintain.

LXP detail duplicates work across two endpoints

getStudentOverview() and getStudentPlaylist() both repeat case checks, default assignment setup, and progress loading. A combined read model or shared loader could reduce duplicate queries and drift risk.

LXP replay completion is split across subsystems

Replay completion depends on JA review completion. That is accurate to the product flow, but it also means troubleshooting replay bugs requires reading both ja.service.ts and lxp.service.ts. A clearer event contract or dedicated bridge abstraction could help.

Tutor generation uses two model calls per session start

The tutor path first plans, then generates the lesson packet. That helps control output quality, but it also adds latency. If startup speed becomes a problem, this is one of the first places to profile.

Extraction jobs run on the live service event loop

/extract creates an async background task in-process. If the Python service restarts mid-job, that work is exposed to interruption. Moving extraction to a durable queue worker would improve resilience.

Extraction apply is operationally heavy

One apply call can create module rows, lesson rows, block rows, assessment rows, option rows, and trigger reindexing. Wrapping the whole apply phase in a very explicit transaction boundary and richer post-apply reporting would make failures easier to reason about.

The extraction audit is already strong enough to power better UX

The pipeline already computes qualityGate, reviewRequired, coherenceScore, reviewFlags, and image assignment summaries. You can expose more of that directly in the teacher UI to prioritize review work instead of treating all extracted sections as equally trustworthy.
